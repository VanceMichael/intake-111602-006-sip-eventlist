# 资料服务接口

旧对话里包含完整版 0 和缺少中间版本的增量版 3；新对话从完整版 0 重新开始，旧对话通知仍能领取。MIME 正文与列表实例通过 Content-ID 关联。

通知采用 SIP 文本头和 multipart/related 正文，Content-ID 使用尖括号封装，RLMI cid 使用对应的无括号值。本地 /subscription 返回已授权对话和可读取的通知位置；仅模拟已建立对话内的接收，不连接真实电话网。

本地服务的资料入口为 `/notify/1`。`fixtures/ordinary.json` 记录当前可预览的资料；`fixtures/transition.json` 保存资料源连续两个发布日期。调用 `POST /control` 并传入 `{"action":"advance"}` 推进发布日期，`inspect` 返回实际请求记录，`reset` 恢复本地源；控制入口不属于远端标准协议。来源分段、延迟和断连均可用场景条目的 `chunks`、`delayMs`、`disconnect` 配置，不需要依赖实际网络故障。

原件目录采用内容摘要寻址，接收凭据独立记录来源、媒体类型和预览结果。单份资料接收不表示来源范围已经读完，也不推断缺失资料的业务含义。

## 席位列表的持续接收

通知是 `NOTIFY` 请求，正文为 `multipart/related`：一份 `application/rlmi+xml` 列表，加上若干 `application/pidf+xml` 依据内容各自的状态。列表的 `<instance cid="...">` 是唯一配对依据，对应的正文段 `Content-ID: <...>` 去掉尖括号后与 cid 相等；正文段在 multipart 中的排列次序不参与配对。找不到对应正文、正文无法解析、Content-ID 重复或正文 `entity` 与列表资源不一致时，该成员记为"不确定"，不能据其判断可接待，也不能让整份名单成为可信完整名单。

### 完整状态与增量状态

- `fullState="true"` 的版本是完整基线：名单整体以它替换，此版本以下的历史版本不再需要。
- `fullState="false"` 的版本只更新列出的资源/实例；一个实例终止只影响该实例，资源终止才清空该资源，与同场馆其他资源、实例无关。
- 收到增量前必须有完整基线。没有基线时增量不写入名单，状态记为"收到报文、未建立名单"。
- 增量版本必须正好是当前版本加一；跳号时保留已应用的内容，但整份名单标记为不最新（`stale`，`missingVersions` 列出缺的版本），已有成员标为过期。缺的版本不会因为收到更高版本而补齐，只有新的完整基线能重新建立可信名单。
- 相同版本号携带不同内容不覆盖当前名单；重复报文、低于当前版本的报文和迟到的 CSeq 都不重复应用。

### 订阅重建与迟到报文

`/subscription` 返回已授权的对话标识（Call-ID）、事件和可领取的通知位置。对话标识变化表示订阅重建：新对话从版本 0 的完整名单重新开始，旧对话保留在 `dialogs` 中以供对照（`supersededBy` 指向新对话）。构造属于旧对话的通知一律标记为 `superseded`，只记录收到与来源，不写入当前名单，因此迟到的旧通知不会覆盖新名单。同一对话内 `CSeq` 不递增的报文同样不应用。

### 查看接口

- `GET /seats/status`：当前订阅的席位视图。`received` 表示已经收到过通知；`complete` 才表示当前对话拥有一份可信的完整名单（订阅有效、没有版本缺口、没有不能对应的成员）。`stale`/`staleReason`/`missingVersions` 说明名单为何不能当作最新；`incompleteReason` 说明名单为何不完整；`generation` 是本进程内第几轮有效订阅；`uncertain` 列出当前不能确定的可接待成员；每个实例的 `source` 记录它来自哪个对话、第几轮、哪个列表版本与 CSeq。
- `GET /seats`：附带所有对话轮次与接收事件（收到、应用、缺口、重建、迟到、忽略）。
- `GET /seats/events`：只取接收事件。
- `POST /seats/notifications`：按原始字节接收一份通知，适合在本机验证；错序、重复和旧对话通知依旧按上述规则处理。
- `POST /seats/refresh`：重新读取 `/subscription` 并据此切换当前对话。

本地服务只在已建立对话内模拟接收；应用每 2 秒（`settleMs` 可调）核对一次订阅与通知位置，收到即处理，不等待实际电话网。
